# ECS Discipline Audit — Assets/Scripts (outside ECS_OPTIMIZATIONS.md baseline)

Scope: every ECS-touching `.cs` file under `Assets/Scripts` (found via grep for
`SystemBase|ISystem|IJobEntity|IComponentData|EntityManager|Entities\.|IEnableableComponent|EntityCommandBuffer`),
excluding `RiceCollectionSystem.cs`'s documented "after" state (still spot-checked; see note).
29 files matched the grep; all were read in full. `Helper*.cs` files were checked explicitly
per the task even where they didn't match the grep (HelperShop.cs, HelperDeploymentSystem.cs,
HelperManagerUI.cs have no ECS/EntityManager usage at all — pure MonoBehaviour game logic,
no findings for them).

Checklist applied to each file:
1. `SystemBase` where `ISystem` would work (unjustified)
2. `.WithoutBurst()` / `.Run()` not clearly justified by managed/main-thread need
3. `AddComponent`/`RemoveComponent` in a loop or per-frame where `IEnableableComponent` would work
4. Missing `[BurstCompile]` on `IJobEntity` structs or `ISystem.OnUpdate`
5. `EntityManager.DestroyEntity()` in a loop instead of batched via `EntityCommandBuffer`/query

## Files checked with no findings (clean / discipline holds)

- `DropperControllerECS.cs` — MonoBehaviour, not a System; batches all entity creation into a single `CreateEntity(archetype, NativeArray<Entity>)` call, only `SetComponentData` (non-structural) per-ball afterward.
- `RiceBallGateInteractionSystem.cs` — MonoBehaviour hybrid bridge; explicitly documents and implements the ECB-via-`EndFixedStepSimulationEntityCommandBufferSystem` fix for the exact sync-point problem this audit is checking for. Justified as non-ECS-system because it needs `Collider.GetComponent`/`.bounds` (managed) each frame.
- `RiceBallWallCollisionSystem.cs` (`RiceBallWallCollisionECSSystem` + `WallCollisionJob`) — exemplary `ISystem` + `IJobEntity` + `[BurstCompile]` (both struct- and method-level, except the minor `OnDestroy` gap noted above), ping-ponged `NativeQueue` for main-thread handoff, zero managed calls in the job.
- `RiceBallRendererECS.cs` — MonoBehaviour GPU-instanced renderer; necessarily main-thread (`Graphics.DrawMeshInstanced`), no structural ECS changes.
- `RiceSpawnSystem.cs` — `ISystem`, Burst-compiled `IJob` for candidate generation, `UnityEngine.Physics.CheckSphere` correctly kept on main thread (Physics API isn't job-safe), gated by a one-time `RiceSpawned` tag so it only runs once.
- `BossHealth.cs`, `BoostBlock.cs` — MonoBehaviours; both snapshot via `ToEntityArray`/`ToComponentDataArray(Allocator.Temp)` then either use `EndFixedStepSimulationEntityCommandBufferSystem`'s ECB (BossHealth) or non-structural `SetComponentData` (BoostBlock). Both explicitly comment that they follow the same pattern as `RiceBallGateInteractionSystem` to avoid sync points.
- `BallDropCompletionManager.cs` — cached query, `Allocator.Temp` reads gated by `checkInterval`, batched `entityManager.DestroyEntity(ballQuery)` for salvage. Best-practice example in the codebase.
- `FPSAudioManager.cs` — cached `EntityQuery` (comment notes it was fixed from recreating the query every call), frequency-gated (`riceCheckInterval`), hard cap of 2000 entities checked per call.
- `RiceCounterUI.cs`, `EntityCountDisplay.cs`, `PerformanceMonitor.cs`, `PerformanceBlackBox.cs`, `SceneSetupChecker.cs`, `BakingDiagnostic.cs` — read-only diagnostics/UI, cached queries, no structural changes.
- `RiceAuthoring.cs`, `RiceSpawnComponents.cs`, `PlayerAuthoring.cs` — component/baker definitions only, no systems.
- `ManualBakingBootstrap.cs` (spawner/spawn-point bootstrap portions) — one-time, guarded by existence checks so it doesn't re-run.
- `HelperShop.cs`, `HelperDeploymentSystem.cs`, `HelperManagerUI.cs` — no ECS/EntityManager usage at all.

## Summary

- **likely-regression: 1** — `RiceBallCollisionSystem` in `RiceBallPhysicsECS.cs` appears to still auto-run every frame despite being commented "TEMPORARILY DISABLED", doing per-frame spatial-hash allocation and O(n) collision work that contradicts the project's zero-allocation goals. This is the one finding worth checking in Unity directly (Systems window / Entity Debugger) before anything else — if confirmed live, it's a real regression.
- **worth-checking: 7** — missing per-method `[BurstCompile]` on `RiceBallDeletionSystem`; per-entity structural changes in `RiceGPURenderer`'s renderer-attach loop (worth checking at 40k-rice scale); an unbatched `DestroyEntity` loop in `BallDropUI.CleanupRiceEntities` (inconsistent with the batched version in `BallDropCompletionManager`); `SystemBase.Entities.WithoutBurst().Run()` in `PlayerTransformSyncSystem` (low-impact, single entity, but a literal instance of the documented "Before" pattern); and unbatched direct `DestroyEntity` calls in `HelperAI.CollectRice` / `HelperWorker.TryCollect`.
- **likely-fine: 6** — a minor missing `[BurstCompile]` on a one-time `OnDestroy`; a one-time, tiny-count `DestroyEntity` loop in bootstrap code; a correctly-batched `AddComponent<Disabled>`/`RemoveComponent<Disabled>` on scene transitions; a documentation/code drift in the already-covered `RiceCollectionSystem.cs` baseline file (`.Run()` vs. documented `.ScheduleParallel()`); and two fully inert dead-code systems (`RiceVisualizerSystem`, commented-out `PlayerMovementSystem`).

Outside these, the DropPuzzle ECS systems (`RiceBallPhysicsSystem`, `RiceBallDeletionSystem` mechanics aside, `RiceBallCleanupSystem`, `SyncBallTransformSystem`, `RiceBallWallCollisionECSSystem`) and the MonoBehaviour-to-ECS bridges (`RiceBallGateInteractionSystem`, `BossHealth`, `BoostBlock`, `BallDropCompletionManager`) consistently follow the `ISystem` + `IJobEntity` + `[BurstCompile]` + `EntityCommandBuffer` discipline documented in ECS_OPTIMIZATIONS.md.
